# Exploratory skills assessment — September 12, 2026 retry

**The skills are useful enough for a workshop pilot. These runs suggest better evidence and context reporting, but do not demonstrate better bug discovery.** All 16 fresh evaluation runs completed after the earlier usage-blocked attempt. Both conditions identified both seeded defects. On the four primary source-plus-runtime cases, the independent condition-blind artifact review averaged **11.75/12 with skills and 10.0/12 without skills**. These are descriptive rubric totals from one pair per case, not a statistically established improvement.

The [machine-readable result](2026-09-12-retry.json) and [evidence archive](2026-09-12-retry/README.md) include the complete retained reports, submissions, integrity grades, hashes, screenshots, HTTP evidence and review reasoning. The strongest difference concerns evidence. In the seeded UI case, the skill run connected an ordinary Cancel click to a browser PUT, its payload, visible feedback and a separate persisted-state read. The baseline showed the incorrect persisted outcome but lacked the browser request capture required by this rubric. The controller audit corroborates the defect, but cannot retroactively supply evidence the candidate failed to preserve.

Thus discovery was **2/2 versus 2/2**, while complete candidate evidence for those findings was **2/2 versus 1/2**. The four control reports contained no unsupported confirmed findings. This does not certify that every possible unseeded defect was absent. Both API controls exercised authorized zero-removal and left Bob's disposable cart requiring an owner restart; their explicit handoffs received a closeout deduction. All owned fixture servers were subsequently stopped.

Request counts varied rather than uniformly improving: with/without skill were 41/56 for the API defect, 48/38 for the API control, 29/36 for the UI defect, and 30/32 for the UI control. These are audited `/api` requests, including browser traffic where present. They are not token, cost or speed measurements.

## Actual hosted Awesome LocalStack

Four additional fresh runs compared API and UI exploration with and without skills at `https://awesome.byst.re`. All four received committed backend, frontend and stack source snapshots. Revisions were backend `8cb264a`, frontend `41e177a`, and stack `4731172`; full IDs and hashes are archived. Local uncommitted work was excluded. No match between these commits and the deployed build was established.

Both API runs independently found the same real contract defect: the live OpenAPI document describes the **401 response from `GET /api/v1/products` as an array of `ProductDto`, while the runtime returns the JSON object `{"message":"Unauthorized"}`**. Each reproduced it twice. The owner independently confirmed it with two public GETs. This is a documentation/schema mismatch; the authentication rejection itself works. The similar cart response was not declared a schema validation failure because its object schema does not require the supposedly missing fields. See the [skill report](2026-09-12-retry/run13/report.md), [baseline report](2026-09-12-retry/run15/report.md), and [independent confirmation](2026-09-12-retry/live-adjudication.json).

Neither UI run confirmed a product defect in the public login, recovery and registration pages. The skill run covered desktop and narrow layouts and retained browser network evidence; the baseline covered desktop with less network evidence. Both respected the task limits. No forms were submitted, accounts authenticated, shared state changed or issues posted. Authenticated cart, checkout, SSO and recovery delivery behavior remain unassessed.

The earlier blanket availability conclusion was too strong. Default Python urllib requests received edge 403 responses containing code 1010, while ordinary browser navigation, curl and an explicitly identified HTTP client succeeded. The preflight now identifies its client and reports the observed response. The local Docker stack remained stopped; the hosted runs supplied actual deployment evidence. Live runs have no complete bug oracle and are not included in the sample's blind numerical comparison.

## Harness repairs and validation

Three practical issues were addressed without changing the evaluated skills or sample implementation:

1. Preflight uses an explicit client identity instead of mistaking a client-specific edge rejection for universal downtime.
2. Audit matching compares parsed routes and flags query-dependent claims for manual review. Previously a legitimate query-bearing request was falsely rejected because the audit stores routes without queries.
3. Future live candidates receive committed source IDs in `source-revisions.json`. Previously those IDs were only in evaluator metadata. All four reported live trials used the same earlier input format, so this improvement is not credited to either condition.

Ten harness tests pass, including the client-identity, query matching and committed-source snapshot checks. The two sample domain tests and scripted browser mutation/control validation passed earlier; their unchanged-artifact evidence is reused. All 16 final artifact integrity grades pass. Integrity checks establish report shape, retained evidence paths, source/skill preservation and corroborated request facts within their limits; they do not automatically establish semantic correctness, browser causality or operating-system isolation.

## What this supports and what comes next

The main weakness is the benchmark's narrowness. It contains only two defect mechanisms in one small app; the UI skill already includes a Cancel/Save example. This is development validation, not a held-out test. One trial per condition cannot separate skill effects from normal run variation. Browser tool choices differed, complete original action traces were not retained, and exact model version, token usage and comparable elapsed times are unavailable. The live deployment was mutable and its skill arms ran before baseline arms.

For a stronger next study, use held-out source-backed tasks, repeat each condition at least three times, retain machine-readable execution traces, fix model/tool versions, and evaluate natural skill triggering separately from explicitly requested use. Include authenticated real-stack workflows in a dedicated disposable deployment with controlled state. Freeze the rubric before runs and retain blind adjudication.

Claude Code's [plugin-evals approach](https://code.claude.com/docs/en/plugin-evals) can inform this Codex workflow: natural task prompts, repeated with/without comparisons, execution checks and artifact grading transfer well. Its native command and Claude-specific tool graders are not directly portable. The locally inspected Codex CLI 0.153.4 has no equivalent plugin-eval subcommand; `codex exec --json` and `--output-schema` provide building blocks for a Codex runner. OpenAI's [skill evaluation guide](https://developers.openai.com/blog/eval-skills) describes this approach. This retry used fresh desktop subagents, not a newly implemented CLI evaluation runner.
