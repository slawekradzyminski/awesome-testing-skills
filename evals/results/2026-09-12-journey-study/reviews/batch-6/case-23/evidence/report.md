**Finding API-01 — low severity: note validation and storage use different length rules.**

The brief specifies notes of 1–160 nonblank characters. With fixture Alice, submit `POST /api/orders/A200/note` with a `note` containing 160 `n` characters followed by one space (161 total). The runtime returns **200**, and a subsequent `GET /api/orders/A200` returns that exact 161-character string. A control request containing 161 `n` characters returns **400** and preserves the previously saved note. Thus, the saved field can exceed 160 characters using surrounding whitespace.

Expected under a 160-character saved-field limit: reject the oversized input with 400 and preserve the prior note, or normalize before saving so the persisted field stays within the limit. Actual: validation checks `len(note.strip())` but storage assigns the original `note` (`app/domain.py:70–74`). This is a live API behavior, not a documentation-only finding. Its severity is low because this assessment observed no loss of valid data or effect on money or authorization. Interpretation caveat: if the intended limit applies only to trimmed content and surrounding whitespace may be stored without limit, this behavior is acceptable; that product interpretation is not established by the brief.

Suggested repair: apply the chosen length rule consistently to validation and storage. Add a regression for 160 nonspace characters plus trailing whitespace, verifying status and a follow-up read, along with the existing 160/161-character controls. Evidence: [boundary requests and responses](note-boundary-http.json), [boundary summary](note-boundary-summary.json), and [reproduction script](note_boundary.py). The investigation restored the original note and verified the entire order matched its pre-investigation state.
